# Build and review a wireflow

Use the wireflow during planning. Let the user start with the whole app, follow one user goal and see which steps, return paths or design decisions need attention. Identify the source briefly, keep reported facts and draft UI assumptions distinguishable, and preserve unresolved policy questions. Use dummy values for real-world side effects.

When an existing implementation blocks a journey required by the brief, deliver the **current, broken flow first**. Reproduce the observed controls and missing action on first open. Put a working alternative in `proposals[].changes`; the first HTML must be built from the baseline JSON. Keep presentation choices open. Give the recovery scenario an expected result beyond returning to a form: use a distinctive input, trigger failure, check retained values, retry and reach the actual success state. The baseline check should fail at the observed gap and the same scenario should pass with `check FLOW.json --with PROPOSAL_ID`. In the HTML, **View proposed fixes** on the affected screen previews the relevant options. Select **Apply fix** to change the dummy, then retry with the same input. The full proposal list is also available in **Flow Verification**. If browser execution is unavailable, identify the model-only result and give the user this path to try.

1. Read [the flow model](references/flow-model.md). Turn the user's brief into a project-local flow JSON with a stable flow ID, screen IDs, and display numbers. Show the controls people need to take action. Include normal use, relevant empty or failed states, and recovery. Use the same shared renderer for every brief. Choose ordinary UI blocks from the model, and put project-specific content in the JSON. Record independent expected outcomes from the plan so checks can catch gaps in the current implementation. For each main journey, consider relevant missing input, failure, cancel or back, and retry. Turn the ones supported by the brief into explicit browser checks. Record unresolved policies as decisions and report which states were exercised. Put screen-specific planning intent under `brief` and relevant conditions under `uxConditions`. Preserve the user’s rationale and label AI-supplied screens as inferred.
2. Run `node <skill-folder>/scripts/wireflow.cjs check FLOW.json` from the project root. For interactive review with a signed-in Codex CLI, start `node <skill-folder>/scripts/wireflow.cjs serve FLOW.json VIEWER.html [PORT]` and open the printed local URL. The screen's **Apply to Wireflow** button sends the request to the local preview for a mockup edit. Use `build FLOW.json VIEWER.html` for a standalone HTML or when Codex CLI is unavailable. A build can include intentionally broken links. Provide links to the preview and source JSON and click a main journey and recovery case when possible.
3. While refining a Wireflow, treat a relevant request in the project chat as a Wireflow edit. Verify the flow ID, then edit the JSON using stable screen and action IDs. Record each completed item in `review.changeRequests` with the original request and concrete result. Reuse a copied Request ID when the request comes from the standalone viewer. For a direct chat request, create a unique ID. Keep unresolved requests pending and omit credentials or unrelated conversation. See [the change request format](references/flow-model.md#change-requests).
4. Rebuild the same HTML output and leave its generated `.live.css` file alongside it. An open preview refreshes itself and announces newly applied changes. Rerun the affected model checks and browser paths, then report which screen numbers changed. The list distinguishes applied changes from updates in progress and delivery to development.
5. **Copy development request prompt** copies the selected applied items for the app development chat. The user can mark delivery after sending the message. When the user pastes that implementation batch or explicitly asks for an actual app update, locate the app code and implement and test the requested behavior. Use the applied result as the scope and the mockup as a reference. Confirm the target project if it cannot be determined from the workspace and request.

Before marking a goal covered, turn the source verb, object, entry context, and observable result into a test. For “save and revisit,” enter a distinct value, leave the result, return to the collection, open the saved item and compare its contents. Check what happens to an existing item on cancel. State whether the test covers the same session or a relaunch. Keep unspecified retention or overwrite policy as a decision. Exercise relevant empty and whitespace-only input.

When the user acts on an image, place a real button in the specified region using `visual.hotspots`. Verify its location inside the scene and click it at that location, then exercise the return or recovery path. Record unsupported gestures or camera behavior as unverified. For a supplied diagram or a spatially meaningful illustration, embed the raster in a visual block as described in the flow model. When the brief calls for imagery without an asset, use a gray `visual` area. Write a short guide inside it naming the photo subject or purpose and set the aspect only when the framing matters.

Match the user's requested interface language for the mockup, planning labels, and tests. Set `review.locale` to `en` for English or `ko` for Korean so the viewer controls and generated diagnostics use that language as well.

Create one `review.requirements` entry per observable requirement from the brief. Link the browser steps that actually check it by setting `requirement` on each step. Use planning decisions for unresolved expectations. This lists what was tested and shows unexecuted items in the canvas sidebar.

For each requirement, put the observable behavior in `expected` and set `origin: "source"` only when the brief actually requires it. Use `origin: "inferred"` for an assumed behavior. When the brief leaves the destination open, list candidate screen IDs in `suggestedScreens` and record the open question in `decisions`. A test may target one candidate to reproduce the current mockup. In a copied request, treat a proposed screen as a design option until the user chooses it.

For independent flow verification, author the expected behavior separately from the mockup and use the XState and Playwright workflow in [independent verification](references/independent-verification.md). Run it when the user asks to verify real clicks or compare the mockup against planning rules, and report the browser viewport checked.

Default to a 390 × 844 CSS-pixel mobile frame. Group screens and their recovery states by user task in named stages. Give each main journey a short scenario title and use its actual action IDs. Start with the whole canvas. Selecting a screen zooms in with neighboring screens visible. Use Overview to return. More canvas tools lets the user choose a different path or device. Highlight only transitions backed by the selected scenario or action. Keep blocked actions and open decisions with the affected screen. The layout uses the same inset on the sides and bottom of each group, and adds that inset to the device corner radius. Keep proposed and missing destinations identifiable. Use an explicit layout from the user when provided. The viewer supports watch presets and direct CSS-pixel width and height entry. Browser scaling preserves the frame dimensions. Keep production changes within the user's requested scope.
